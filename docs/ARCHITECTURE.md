# Architecture

## Overview

```
            ┌────────────── src/terrain (pure, no DOM/three) ───────────────────┐
 generator ▶│ Terrain: density grid + dirty chunks                               │
 (seed)     │   sample · normal · raycast · carve                                │
            │ ChunkMesher: chunk ──▶ positions, normals, colors, pbr, indices    │
            └───────────────▲──────────────────────────────┬─────────────────────┘
                            │ stable interface             │ ChunkMesh
              gameplay (bugs, projectiles, picking)        ▼
                                                   src/render: ChunkRenderer → three.js
```

The boundary that matters is the one on the left: gameplay only uses `sample`, `normal`, `raycast` and `carve`. Whatever draws (three.js today, something else tomorrow) only receives `ChunkMesh`.

## Data model

- A world of `W×H×D` cells (default 160×96×160 = 5×3×5 chunks of 32; `?map=3x2x3` gives 96×64×96). One world unit = one cell.
- Density samples at the grid points: `(W+1)(H+1)(D+1)` floats. `< 0` is solid, `> 0` is air. The value is an *approximate* signed distance (not exact after several operations), in cell units, clamped to ±6.
- The outer layer of the world is always air, so the surface is closed (no "holes" at the edges). `carve` never opens it.
- `scorch` (0–255 per sample) stores the burn mark; `material` (one id per sample, `materials.ts`) says what the surface near the sample is made of. Both are visual only and feed into the vertex colors; gameplay never reads them.
- `dirty`: the set of chunk ids to re-mesh.

## Procedural generation

A generator is `(terrain, seed) => void`; it starts with `terrain.beginGeneration()` (all air, no material, no scorch) and ends with `terrain.commitGeneration()`. Scenarios (`scenarios.ts`) pair a generator with its look (page background and fog colour); the menu and `?scenario=` pick one.

### Car Dashboard (`generators/car.ts` + `carPlan.ts`, `?scenario=car`)

The owner's car dashboard, door to door, from photos and a video (no brands, its own beetle emblem), on its own 10x4x5 map at the desk's scale (2 units a centimetre). `carPlan.ts` is pure data and arithmetic in base units (320×128×160, `carScale` places it on any map), shared by the generator and the render. Pictures (instruments, radio, climate panel, map, papers, garage) are canvases drawn at load (`carTextures.ts`): generic words and signs only.

### SDF stamps (`sdf.ts`)

Primitives: sphere, box (rounded, optionally rotated about one axis), cylinder, capsule, torus, capped cone (along y; a loudspeaker cone); `distance(shape, p)` is exact. A stamp (`add` = union, optionally smooth; `cut` = subtraction) writes one shape into the grid, visiting only its bounding box plus 4 cells, so hundreds of parts stay cheap. Beyond that padding the grid keeps at most the clamp value (6), and `raycast` steps 0.6 × the sample (3.6 < 4), so it cannot jump over a part. `add` also sets the material of the samples where the shape owns the surface; `paint` changes only the material inside a shape (the raw inside of a box built from another material). Stamps never write the outer two layers (the world stays closed), and never write an exact 0 (a surface exactly on a sample would make degenerate triangles). Rotations use exact (cos, sin) pairs (e.g. √3/2 for 60°): no `Math.sin/cos`.

`addHidden` adds a solid that gameplay sees and the render does not: it uses the `COLLIDER` material, whose roughness is an impossible value (`HIDDEN_ROUGHNESS` = 3), and the terrain material discards those fragments (colour and shadow). It sets the material only on samples that were air, so a collider never recolours the part it overlaps. Thin-wire colliders stop ~1.2 units short of each end, where the wire enters its part: there the mesher would blend the collider's dark colour into the part's border.

Shapes are composed with SDF operations: union `min(a,b)`, subtraction `max(a,-b)`, intersection `max(a,b)`. The maps are built this way (see SDF stamps above).

Determinism: integer-hash noise (`noise.ts`), seeded PRNG (`createRng`). No `Math.random`/`Math.sin` in generation, so the same number gives the same map on any device. The tests check this.

## Meshing (Dual Contouring / Surface Nets)

Vertex colours come from `shadeVertex` (`shading.ts`): the material of the cell's corners gives the base colour (where the corners disagree, their colours and finishes are blended, trilinear and weighted towards solid corners, so material borders follow the surface instead of stepping) (GROUND is grass on top and rock on the sides), with a little noise, darkened by scorch and by ambient occlusion. The occlusion comes from the density field itself: the mesher probes outward along the normal at 1, 2 and 3.5 cells, and where the field says something is closer than the probe, the vertex sits in a crease and gets darker (3 samples per vertex, in the worker). The mesher also writes a `pbr` attribute per vertex (roughness, metalness, glow) from the material table. Glow is signed so it blends across borders: towards +1 an RGB light, towards −1 a fan blade.

Per chunk, in three steps (`mesher.ts`):

1. **Vertices.** For each cell whose 8 corners have different signs, one vertex. Where it goes depends on the mode, chosen per scenario (`Scenario.sharpEdges`):
   - **Dual Contouring** (built scenarios, e.g. the PC): in cells that hold a sharp feature (two crossing normals more than ~37° apart), the point that best fits the tangent planes at the cell's edge crossings (a 3×3 least-squares problem, the QEF, solved around the crossings' mass point with a small bias towards it, and kept inside the cell). Box edges and corners stay sharp. The plane normals must be right: the trilinear field blurs them near an edge, so each crossing takes its normal from the most linear of the 4 cells around its grid edge (smallest trilinear cross terms): such a cell sees one face only, so its gradient is that face's normal. A test checks that a box corner off the grid comes out within 0.1 of the true corner (Surface Nets: more than 0.3 away).
   - **Surface Nets** (natural terrain; no map uses it now): the average of the edge crossings. Smooth; it rounds every edge. Dual Contouring also uses this point in smooth cells (tubes, rounded rims): the QEF fit on a gently curved surface snaps vertices to small ridges, a saw-tooth along the curve.

   The vertex normal is the analytic gradient of the cell's trilinear interpolation. In sharp mode the terrain shader also uses the triangle's own normal where it disagrees strongly with the interpolated one, so hard edges are shaded hard.
2. **Lazy emission.** Output vertices are only created when some quad uses them.
3. **Quads.** For each grid edge with a sign change, one quad connecting the 4 cells that share it; the winding depends on which side is solid.

**Seams.** Vertices are computed over the chunk's cells `[start-1, end)` and depend only on the global grid, so two neighbouring chunks produce exactly the same vertices on their shared boundary. Each chunk emits only the quads whose source edge lies inside it, so no quad is duplicated. The tests check this (zero open edges after welding positions).

**Performance.** No allocations in hot loops; scratch buffers are reused between calls (so one mesher instance serves one thread at a time). Surface Nets ~2–3 ms per chunk; Dual Contouring about twice that (in the workers, so it does not reach the main thread).

**Known limitations.**
- Sharp round rims (a cylinder's flat top) show the grid as small steps in Dual Contouring: give round parts a rounded rim of at least ~1 cell.
- Walls thinner than ~2 cells can vanish or break up: the scenario design rule is ≥ 2 cells for parts and gaps.
- There are some non-manifold edges (≈100–200 per map); this is normal for this algorithm, and the test only checks they do not blow up.
- About 0.1% of faces end up wound against their normals in very thin geometry.
- Per-cell normals can show slight faceting; if it bothers us, smooth them with the neighbouring cells' normals.

## Collisions and picking

No mesh colliders. `raycast` does sphere tracing over `sample()` (step `max(0.25, d·0.6)`, refined by bisection) because the field is only approximately an SDF. Bugs and projectiles will test `sample()` and the gradient (`normal()`) directly: this is cheaper than rebuilding a collider after every explosion and gives normals for free. Caution: the minimum step of 0.25 can pass through walls thinner than that.

## Bugs (`src/game/`)

`src/game/` is pure like `src/terrain/`: no three.js, no DOM. It sees the terrain only through `TerrainField` (`sample`, `raycast` and the world size), which `Terrain` satisfies.

- **Species** (`species.ts`): one data object per species. Physics reads the radius and the movement numbers; the renderer reads the body proportions (legs, body length, abdomen, head, antennae, colors). A new species is new data, not new code.
- **Fixed timestep.** `Bug.step` advances one tick of `DT = 1/60` s with one discrete input (`move`, `turn`, `jump`). `main.ts` runs as many ticks as real time requires and renders between the last two ticks (interpolation), so the simulation does not depend on the frame rate.
- **Collision.** The bug is one sphere. `surfaceDistance` estimates the distance to the nearest surface as `sample / |gradient|` (central differences, half a cell). It divides only when `|gradient| > 1`: that corrects the ground, which is generated as a vertical distance and overestimates on slopes; in concave corners the gradient averages two normals (`|gradient| < 1`) and dividing would let the sphere sink into walls.
- **Contacts.** A contact with normal Y ≥ 0.64 (~50°) is ground, anything else is wall or ceiling. On ground, contacts push the sphere straight up, so a bug standing on a slope does not creep downhill; on anything steeper they push along their normal. Velocity into the surface is removed.
- **Crawling.** Every bug walks on any surface: up and down walls, round edges, under overhangs. While it holds on (`grounded`, whatever the slope) it keeps the surface's normal, and its heading is its horizontal facing turned by the least turn that takes the vertical to that normal: facing a wall is up it, facing away from it down, along it level (at 0.75 of the walking speed). Under a ceiling (normal Y below −0.8) that turn is not defined: the heading is carried along, and the facing is taken back from it on the way out. Walking into another surface squarely enough (cosine below −0.45) takes the bug over onto it. Each tick it stays in touch: on ground it is pulled down by up to 0.3 units; on a steeper surface or past an edge it closes exactly the gap left, towards the nearest point, so it goes round edges without slipping or hopping. A resting bug stays where it is, also on a wall. It lets go when it jumps (off a wall: away from it and up), when it is pushed (explosions) and when nothing is left within reach (craters need no special case). Falling, it lands on ground only, unless it walks forward into a wall at less than 18 units/s: then it catches hold. At the world's outer layers a crawling bug turns back. Random walks of half an hour a map, on every scenario, end with no fall at all.
- **Bugs against bugs.** After every tick `Match.keepApart` puts apart any two live bugs nearer than 1.15 of their radii together: the one that moved is put back (both, if both did), along its surface, never into the terrain. One that comes down on another slides off it.
- **Aim.** `Bug.direction` turns the aim (front, and away from what it stands on) into the world: level ground and slopes up to ~20° aim by the world, walls and ceilings (from ~50°) by the surface, easing in between. So on a wall a shot leaves along the bug's own front, off the wall. The aim goes up to exactly vertical. On a bounded map a shot that reaches the top stops there and falls back (and may hit its shooter); only the sides lose it.
- **Air.** Gravity, terminal speed, no air control. Moves are split into substeps of at most 0.35 radius, so the bug cannot skip through walls. The downward speed at landing is kept in `lastImpact` for fall damage later.
- **Death.** Below `y = -4` the bug has left the world. The outer shell of the box is air, so being thrown off the edge or falling through a hole that reaches the bottom both end there (a crawling bug turns back at the edge).
- **Determinism.** Only `+ - * /`, `Math.sqrt`, `Math.ceil`; turning uses a small-angle series instead of `Math.sin/cos`. A test scans `src/terrain` and `src/game` for banned `Math` functions, and another one replays 10 s of scripted input with explosions twice and compares every bit.
- **Cost.** About 0.5 µs per bug per tick (`npm run bench`).

Render side: `BugView` builds the body from spheres and cylinders, leans it into the ground normal (smoothed), and animates a tripod gait from the actual ground speed. Each leg of a standing bug turns about its hinge so its foot rests on what is drawn under it, and the body rides at its height over that (render only). `DrawnGround` answers this: a `raycast` down the density field, then a short ray against the drawn parts near that point (smooth parts and their hidden bodies differ by a fraction of a unit; the window is 1.3 above to 0.75 below, and below only where the terrain is a hidden `COLLIDER`). It indexes the drawn triangles of a map in a grid of 4-unit cells, 3 ms per frame after the map loads (car: ~490k triangles); a query costs 1-5 µs. Parts that moved since, hidden parts and the insides of craters do not count; it indexes again after a turntable turn. Dead bugs and grenades lie on the same ground. After a blast, a small drawn part (an LED, a screw) near it with nothing solid left in or at it goes too (`dropLoose`), so none hangs in the air. `FollowCamera` moves the orbit camera and its target together, so the player keeps the angle and zoom; panning is off while following. `Controls` (`src/input/controls.ts`) uses physical key codes (WASD works on any layout). The player can change each action's main key in the menu (`ui/keys.ts`, saved in `localStorage`); 1–4, N and Escape stay fixed. Fire is Q by default. While the right button turns the view, A / D turn the view too (slowly at first, then at the species' turn rate), and the bug follows the view: in `Bug.step` a facing from the view wins over the turn keys.

## Match: turns and weapons (`src/game/match.ts`)

`Match` owns the teams, the projectiles, the wind and the turn state. Like `Bug`, it advances in fixed ticks with one discrete input per tick (`MatchInput`: walk, run, turn, jump, aim, fire held, weapon). The whole match is a function of the map seed, the match seed and that input stream, which is what multiplayer will send.

- **Turn flow.** `aim` (30 s: walk, jump, aim, choose a weapon, fire) → `flight` (projectiles fly; the shooter has 3 s to retreat, without firing again) → `settle` (wait until every bug and projectile is at rest, at most 10 s; bugs at 0 health die here) → the next team that still has bugs. Teams alternate; inside a team the bugs take turns; dead bugs are skipped. Getting hurt on your own turn ends the aiming. At most one team left → `over`.
- **Aiming.** The aim pitch is a 2D unit vector `(aimH, aimV)` in the vertical plane of the bug's facing, rotated with the same small-angle series as the facing (no `sin/cos`). Holding fire charges the power for 1.2 s; releasing fires, and a full bar fires by itself.
- **Wind.** A new horizontal acceleration per turn, from the match's seeded PRNG. Each weapon says how much it feels it.
- **Projectiles** (`projectile.ts`): a point of radius 0.3 under gravity and wind, in substeps of at most 0.3 units. Shells explode on the first contact with terrain (`sample` below the radius) or with a bug (the shooter is immune for 8 ticks). Grenades bounce off the terrain (normal from `surfaceDistance`, restitution and friction per weapon), come to rest, and explode when the fuse runs out.
- **Explosions.** `carve` + damage that falls off linearly up to 1.6 blast radii from the centre (distance measured to the bug's surface) + knockback away from the centre with an upward bias. A thrown bug can take fall damage when it lands (above 15 units/s).
- **Weapons** (`weapons.ts`) are data. Short Circuit adds an arc that jumps to the nearest bugs one after another (ties go to the lower unit id, so it stays deterministic). Soldering Iron has no projectile: it carves a row of spheres along the aim.
- **Bodies for drawn parts.** At the end of their generation, the tower, speaker, fridge, microwave and desk give a hidden body (`COLLIDER`) to every drawn `part`, `wire` and `rod` that sticks out into clear air without one (`bodies.ts`). Samples near an existing surface are never touched, so floors and walls keep their shape; see-through and very small parts are left alone.
- **Silk.** Species with `silk` (the spider) have Web Shot (`kind: 'web'`, `species`): its ball opens a `Web` on the surface it lands on (`Match.webs`: middle, normal, turns left, strength). Other bugs standing in it walk at `WEB_SLOW` and cannot jump; pulling for `WEB_TEAR_TICKS` on their turns tears it, a blast takes it, and it goes after `webTurns` turns. A turntable carries its webs. In the air a spider's jump takes hold of a thread from the last surface it stood on (`Bug.thread`): it comes down at a limited speed; a push, or that surface blown away, cuts it. Web Bow (`kind: 'arrow'`) is a special attack: `Weapon.sceneTicks` gives the match a `special` phase as soon as it is picked, for its scene; then back to `aim` in a `stance` (it turns and aims on the spot, `MatchInput.pitch` carries the mouse's tilt, charging draws the string; another weapon calls it off). The turn's clock stands still in the scene, and after a hit the match waits `LINGER_TICKS` before the shooter may walk away. Its dart is fast and flat (`gravityFactor`), hurts only the bug it hits, by its speed, and opens a great web where it ends. The scene is render only: `render/gpu/bowScene.ts` (the stance, set through `BugView.pose`; the scarf, the flames, the sign on the ground, the bow, the dart, the trail, the burst), `bowCamera.ts` (its cuts, kept clear of terrain) and `StageFx` in `gpuStage.ts` (a pass of its own for lights, the dimming by distance, the edge blur). It slows the loop (`timeScale`): the same ticks, later. `__debug.advance(seconds)` plays a paused game on for captures. `render/webs.ts` draws webs, threads and the strands on held bugs.
- **Ant Column** (`kind: 'column'`, the ant's special attack) works the same way up to the shot. The fire makes a `Match.column`: a marcher (`MARCHER` in `species.ts`, a bug's physics without a unit) that walks by itself, over walls too, for up to `MARCH_TICKS` by the power; the turn keys steer it. Its path is kept (`columnHead`), and the first enemy within `SWARM_REACH` of it is swarmed for `SWARM_TICKS`, bite by bite; then the ground under it collapses (a blast) and the match lingers. A column that meets nobody collapses where it ends; one that falls off is lost. The scene is render only: `render/gpu/columnScene.ts` (the stance, the cracks and holes, the 180 small ants, which march along the path and then run, climb legs and sit on the victim's lumps, the collapse) and `columnCamera.ts`. Its small ants are placed after the bugs are posed (`late`). It shares the bow's two lights: lights of its own would cost every material.
- **Blackout Swarm** and **Hard Shell** (cockroach). The weapon kind is `brood`: its scene plays, then in its stance the input carries `mark`, the spot under the player's pointer (plain numbers, rounded, part of the tick's input); `Match` puts it on the nearest surface, within `markRange`. Fire sets `Match.brood`: it covers every enemy within `coverRadius` of the mark at `BROOD_COVER` ticks (`cover`), bites, and flees at `BROOD_LIGHT` (`lights`); no crater. `BroodScene` draws it: the stage's `black` and `reveal` uniforms put the lights out (moonlight is left), eyes are drawn on their own, the ring is projected on what the view shows (from its depth), and each cockroach's run is laid over the drawn ground when it sets out. `BroodCamera` holds the view the player marks from. Hard Shell is `BugSpecies.shell`: `Match.damage` leaves the bug at 1 health at the first blow that would kill it, and lets nothing more through in that turn (`shell` event; the shell is drawn cracked).
- **Computer opponent** (`src/game/brain.ts`). A `Brain` gives the match one `MatchInput` per tick, like a player; it never changes the match. It solves the arc to each enemy for several flight times (wind and gravity are constant accelerations), flies each with the real `Projectile`, and scores the damage (kills more, its own side negative). With no good shot it walks clones of its bug (`Bug.copy`) eight ways, tries shots from where they end, and goes there; with none at all it blows away what stands between, or digs. It aims with the same keys and limits, tunes the charge to the aim it got, and a skill makes its hand unsteady. After the shot it takes cover. About ten tries per tick (under 2 ms at worst, ~4 µs on average), pure and seeded. From 12 matches per map, normal against normal: about 70% of the turns hurt an enemy, 4 to 6 minutes a match; hard beats normal 3 in 4, normal beats easy 4 in 5.
- **Skill loader** (`Match.skill`, 0 to `SKILL_FULL` per team). It loads at every turn of the team, with the damage it does (not by a special itself) and takes; firing a special empties it, calling one off does not. `Match.has` says a species owns a weapon (the keys, the HUD), `Match.canUse` that it can be used now; the `skill` event tells it is full. `ui/skillCard.ts` draws the card: the coloured face is clipped to a wedge (no conic gradient: the first gradient painted over the game costs a frame of ~100 ms).
- **Balance** (`npm run balance -- [seeds] [special chance] [skill] [scenario]`). The computer plays itself, every pair of species both ways round on every map. Two layers: with no specials (`0`) the species win 47–53%; with free specials now and then 49–51% (432 matches each, normal). The species' health (`BugSpecies.health`) evens out their abilities. A special does 1.2 to 1.7 times a basic shot per use. With the skill loader: 48–52% (288 matches), specials about one shot in ten.
- **Sound** (`src/audio/`). There are no audio files: `sounds.ts` holds every sound as a recipe over the pieces in `dsp.ts` (pure, seeded, so the tests check each one: finite, no clicks, seamless loops). `sound.worker.ts` computes them all while the page loads (~1.3 s of worker time, ~120 s of sound). `SoundEngine` plays them with Web Audio: the context opens at the first click or key, sounds in the world have a place (heard from the view), the world goes dull while a scene slows time, a scene's own sounds do not, each map has an echo and an ambience, a limiter ends the chain. `GameSounds` is where the game is heard: `tick` after every match tick (events, steps, bounces, fuses), `frame` every frame (loops, and the scenes' cues, which follow the scenes' own clock, `sceneTime`). A new sound is a recipe plus a line there; a new map needs a `room:<id>` recipe (tested). Settings are kept in the browser. `__debug.sound.log` lists what was played.
- **Setup screen** (`ui/setup.ts`, `render/gpu/heroes.ts`). It comes first, unless the address says `?play=1`, `?perf=1` or asks for a debug camera. The map is there behind it, at rest; the picture is tinted in the teams' colours either side of an electric seam. That, and the two large fighters, are a layer of their own (`MenuLayer` in `gpuStage.ts`: a scene and a pass, composed over the finished picture; while no menu is up it is not in the pipeline and costs nothing). `heroes.ts` drives two real `BugView`s by hand; `heroDress.ts` gives them the finer looks (coats shared per team, since shaders are slow to make; every fighter is made once and kept); the bugs of a match wear the same (what is one bug's own, such as its death or a special attack's glow, reaches the shared materials as uniforms per object; hairs and spines are drawn within 60 units of the camera); `heroStage.ts` is the floor and the things of each map. A map is changed in place: the colours shut, `Terrain.resize` and the generator run, the colours rip open once the chunks are meshed. The DOM part writes a `SetupChoice`; `startMatch` in `main.ts` makes the match of it and keeps it in the address (`?teams`, `?players`, `?size`, `?turn`, `?wind`, `?seed`, `?scenario`). `ui/lettering.ts` is the game's lettering (strokes as data, drawn as SVG). At the end of a match `EndScreen` shows the winner, the survivors, the turns and the best hit. A map's shaders are made all at once, on the GPU's own threads, before anything of it is drawn (`Stage.warm`; meanwhile the last picture stays): a map seen for the first time stalls for well under a second instead of 3 to 4. The menu has a theme of its own (`menu` in `audio/music.ts`). Until the first frames run smoothly a loading sign stands before it all. Cost on an RTX 4070 at 2560×1440: ~5.4 ms GPU per frame with the menu up.
- **Items** (`game/items.ts`, `render/gpu/itemViews.ts`). A box may set out at the start of each turn (its own random numbers, so the winds do not move): its place is found by letting a bug walk there (the small ants carry it along that very path) or by a place a bee can drop it on. It falls when it loses its ground, a blast destroys it, a bug that touches it opens it (`Match.open`). What is found to be used later is in `Match.stock` (uses per team and weapon; `Weapon.found`). Thermal paste is a web that holds only the other teams. The computer walks to boxes it can reach.
- **HUD** (`ui/hud.ts`, `ui/emblems.ts`). Above, the duel: both teams' health (what was lost trails behind), a chip per bug, how far each special is loaded, the clock and the wind. Below, the hand: a card per weapon, fanned, the special's card last (it loads); the hand leaves the screen in the computer's turn. Labels and damage numbers stay out of the strip at the top; the active bug's label lies under its feet.
- **Music** (`src/audio/music.ts`, `MusicEngine.ts`). A theme per map is data: tempo, scale, the chord of each bar, figures in steps of the scale, a melody (its resting notes settle on the chord), drums in sixteenths. Small wavetable instruments play it on a worker (`music.worker.ts`, 1 to 2 s a map) into three stereo stems of the same length, what rings past the end written into the start, so they loop without a seam: `base` (chords, bass), `groove` (melody, drums), `tension`. The stems' levels follow the match (`GameSounds.playMusic`): tension in a turn's last 8 seconds or when a team is under 30% health; behind a low-pass in a special attack's scene; silent in a blackout; ducked by blasts. Only the current map's stems are kept. `MusicEngine.beat` is there for things that move to it.
- **Confined maps.** A scenario can say where a bug may stand and walk (`confine`, a pure function of the place): spawns outside it are tried again, and a crawling bug turns back at its limit, as at the edge of the world. A bug thrown outside may walk back. The car uses it (`insideCar`): not the outer side of the windows, not the cut ends of the doors, not the bulkhead under the dashboard.
- **Deaths.** Bugs at 0 health die at the end of the turn; the match then waits `DEATH_HOLD_TICKS` (1.6 s) before the next turn, and the camera looks at the first one that died. `BugView` rolls it onto its back with a hop, kicks and curls its legs, and dulls its colours; the body stays where it died and falls (render only, a `raycast` down the density field) if the ground under it is blown away. A bug that falls out of the world is just gone.
- **Turntable.** On a map with one (`MatchOptions.turntable`), a `spin` phase after `settle` turns it a quarter and carries what rests on it (see the Microwave section).
- **Events.** Every step fills `match.events` (turn, fire, explosion, arc, dig, damage, death, over). The render reads them for effects and floating damage numbers; the game never reads them back.
- **PRNG.** `game/` uses `createRng` from `terrain/noise.ts`: a pure utility, not part of the terrain representation.

Render side: `UnitLabel` (name and health above each bug, redrawn only on change), `FloatingTexts`, `ProjectileViews`, `LineFlashes` (arcs, tunnels), `AimView` (a short pointer of fixed length along the aim: it shows the direction only, never the range, so it cannot be read as where the shot lands; plus the active-bug marker). The camera follows the first projectile in flight, then stays on what it hit (the bug it hurt most, or the spot), otherwise the active bug. Damage keeps the next turn waiting for `LOOK_DAMAGE_TICKS` (1.8 s), a blast that hurts nobody for 1 s. A player who walks during the retreat gets the view back at once. Each turn starts with a short glide to a chase view behind the active bug, looking where it walks (`FollowCamera.chase`: 15 units back and a little above; with terrain right behind the bug it first climbs, and only then comes closer). While the bug aims, the view turns with it, so forward stays into the screen. The other way round too: the right mouse button orbits the view, and while it is held (and for a moment after, while the orbit damping settles) the active bug faces where the view looks. That is a `faceX`/`faceZ` in `MatchInput` (rounded to 1/4096, so it travels with the tick's input like any key); the bug takes it as its facing. Keys get fine control from a ramp: turning and aiming start at 15% of their rate and reach full rate after 0.6 s held, so a tap moves a fraction of a degree. The HUD shows the aim angle to one decimal. The intro glides from the scenario's start pose into that same chase view. When terrain (a floating island) is between the target and the camera, `FollowCamera.avoid` (with `raycast` against the density field) first raises the camera, in steps up to ~60° above the angle the player chose, until the view is clear; only if that is not enough does it move the camera in front of the terrain. It keeps the player's own angle and zoom apart from its corrections, and eases back to them once the view is clear. `Controls` turns keys and the on-screen pad (`[data-code]` buttons, pointer events: mouse and touch) into `MatchInput`. In dev builds, shift+click blows up the terrain under the pointer.

## Explosions

`carve(p, r)` does `d = max(d, r - dist)` in a box around the sphere, updates `scorch` and marks as dirty the touched chunks **plus their neighbours** (they share boundary vertices). On average ~3 chunks per explosion with r=6.

## Rendering

One terrain material (`terrainMaterial.ts`, TSL) takes roughness and metalness per vertex from the `pbr` attribute, so metal reflects and plastic does not. Light: an image-based environment (three's `RoomEnvironment` through PMREM), a weak hemisphere light, and one directional key light with soft shadows (4096² map). ACES tone mapping.

### The renderer

**Every map uses WebGPU** (`render/gpu/`): three's `WebGPURenderer` with TSL node materials. `Stage` (`render/stage.ts`) is its interface: scene, camera, controls, the terrain material (`TerrainLook`), `setScenario(sc, layout)`, `render(seconds, dt)`, and an optional GPU timer. The old WebGL path went with the last map that used it. The renderer's parts:

  - `terrainMaterial.ts`: the terrain material in TSL (same inputs), plus glow: RGB diffusers show one shared hue that sweeps teal→magenta (render-only time, `glow.ts`; every hue is scaled to one level, a mix of luminance and the strongest channel, with pure blue lifted towards a real blue LED so it does not read dim), and fan blades carry a bright stripe that turns, so static blades read as spinning.
  - `atmosphere.ts`: distance fog measured from the camera (clear for ~40 units, the scenario's fog colour by ~150), a thin floor layer tinted by the nearby RGB lights, corners that fall to near-black, the dark-room backdrop, and the render-only glass panel (Fresnel, green edge tint, procedural smudges, the key light's highlight).
  - Post (`gpuStage.ts`): one MSAA scene pass with colour, emissive and depth; half-resolution ray-marched god rays (16 steps) from the key light's shadow map, which is fitted tightly around the enclosure so the rays stay inside it; bloom of the emissive buffer only; heat shimmer; ACES.
  - `dust.ts`: 3,000 seeded dust motes advected by an analytic airflow in a compute shader; drawn as sprites never smaller than ~1.6 px (they fade instead of flickering).
  - `heat.ts`: heat shimmer, a screen-space refraction inside the projected rectangles of the layout's `heat` boxes. `leds.ts`: blinking activity LEDs.
  - Smooth stand-ins (`lightOverlays.ts`, `heroOverlays.ts`): at one sample per unit, thin or round hero parts (fan rings, light bars, fan rotors, cooler tubes and cables, pump cap, capacitors, traces, RAM bodies, solder beads, grommets, mounting screws, dust bunnies, and the generic `part` details: ports, slots, shields, drives, connectors) mesh lumpy. A `wire` is a soft cable along a polyline the generator computes (`parts.wirePath`, a Catmull-Rom curve in plain arithmetic): the SATA cables are also in the terrain (0.3 thinner than drawn, and short of the bends into their plugs), so bugs walk on them; the antenna leads are too thin and are render-only, like the dust bunnies and the wall panels. A generic `part` feature (box or cylinder, colour, metal, roughness, glow) lets a generator add small details: the terrain gets a block just inside the render shape (no coinciding surfaces, so no z-fighting), the renderer draws the clean shape. Render-only smooth meshes sit just outside the terrain surface and hide it; the terrain under them stays the real, destructible part. Every stand-in material is cut by the craters (`craters.ts`): the main loop passes each explosion and tunnel to the stage, which keeps the carved spheres (as `Terrain.carve` makes them) in a uniform array, and a `maskNode` drops the fragments inside them, in colour and in the shadow pass. So a crater opens the same round hole in a stand-in as in the terrain under it, exactly where it was hit. Through such a hole the inside shows: the hidden body's crater wall is drawn (the terrain material shows `COLLIDER` only within a crater's shell, charred), and the cut materials are double-sided, so the far side of a hollow part shows too (about +0.1 to +0.4 ms of GPU time at 2560×1440). The rings and bars carry the RGB glow; the rotors carry the turning light stripe.
  - Key light: warmer (0xffb878) and steep; a scenario may set its own direction, colour and intensity. It lights the scene evenly: an earlier version cut it with window-blind slats above the glass, but their stripes crossed every part and were removed. The dust motes shine only where the key light came in through the glass (traced analytically to the top of the scene).
  - Emissive target blending: the scene pass writes colour and emissive (MRT); the emissive target is set to blend like the material (`MaterialBlending`), otherwise every transparent surface (glass, labels) overwrites the emissive under it and the glow behind it loses its bloom. The glass writes emissive 0 with alpha 0, through a material `mrtNode`. Such a material cannot draw outside that MRT pass (it has no colour output there), so it lives on `POST_LAYER`. The camera turns that layer on only once the post pipeline exists, and shader precompiles skip it.
  - Labels: name and health plates are in a separate `hud` scene, drawn as its own pass and composited after tone mapping and FXAA, so heat shimmer, bloom and FXAA never touch them. They keep one screen size, and they are anchored by their bottom edge above the bug and snapped to whole pixels for the exact frame drawn (`placeLabels` in `main.ts`, also before every debug capture). From afar the bugs are drawn up to 1.7× larger, and they are not fogged, so they read in the dark corners (render only; physics is unchanged).
  - Precompile: `compileAsync` after the first frames, so the first look at something new does not stall a frame on a shader compile.

  Without WebGPU the same code runs on three's WebGL2 backend, without the motes (no compute) and without timestamps.

Per scenario (`scenarios.ts`), the renderer also takes: the key light's direction, colour and intensity; the fog's clear distance and span; how dark the map's edges fall; the backdrop colour; and the chase camera's lowest angle (higher over tall walls). The terrain material reads special shadings from codes in the glow channel (`materials.ts`: fan, wadding fuzz, wood grain, vinyl peel); the mesher blends the channel across borders, so a code that lies between two others is crossed along their border: the vinyl's mottle only applies on near-black surfaces for that reason.

A generator can describe its render-only features in a `SceneLayout` (`generators/types.ts`): fans, the pump, light bars, LEDs, heat boxes, the glass height and the enclosure. Gameplay never reads it.

### Debug hooks, camera work and review tooling (`src/debug/`)

Shared by every scenario (the menu's **free camera** button reloads the map with `?fly=1`, and back; its **cinematic camera** button the same with `?flythrough=1`, with a small bar to pause and leave that hides while the mouse rests, and no labels; `?hud=0` drops the bar, for measurements): `?pose=1..6` (a fixed pose; render-only time runs at a fixed 60 Hz step for 6 s and stops, so a pose renders the same image every run), `?flythrough=1` (a 60 s closed Catmull-Rom path, tabulated at even speed and lifted where it would come within 9 units of the terrain inside the map), `?fly=1` (free camera: WASD, Q/E, mouse look with pointer lock, Shift/Ctrl, wheel for speed, R to reset), `?perf=1` (frame intervals and GPU time per frame from timestamp queries; `__debug.perfRun(60)` returns average, p99 and max; `__debug.perfDownload()` saves JSON), `?res=WxH` (fixed drawing-buffer size) and `?hud=0|1`. Poses, start view and path come from `debug/views.ts` (per scenario, with a generic fallback), derived from the map size and the layout only. `__debug.capture(name, {t, dt, jpeg})` saves the canvas through the dev server (`captures/`, git-ignored); `scripts/capture-poses.md` and `scripts/review-pack.sh` build the packet for the visual review (poses, a 10 s fly-through as video, contact sheets, consecutive-frame bursts and their differences). `scripts/topview.ts` prints a top-down map of a layout without a browser.

### Meshing workers (`src/render/MeshWorkers.ts`, `src/workers/mesh.worker.ts`)

- After each simulation step, the dirty chunks are sent to a pool of module workers (cores − 1, at most 4), spread evenly so the chunks of one explosion mesh in parallel.
- A job carries only the samples its chunk reads: the chunk's cells plus a pad of 6 samples on each side (one cell for the mesher, the rest for the ambient-occlusion probe): a box of 44³ samples, densities, scorch and material packed in one ~510 kB buffer (`terrain/region.ts`). The buffer is transferred, and it comes back with the result for reuse. The grid itself never crosses threads.
- Each worker keeps a mirror grid in which only the regions it was sent are current. That is all the mesher reads, so it runs the same `ChunkMesher` unchanged (both modes; the request says which). A test checks that a mirror mesh is bit-identical to the original for every chunk.
- The meshes are transferred back (no copy). The whole batch is applied in one frame, so neighbouring chunks of an explosion change together and the seams never open.
- Results are dropped when a newer request for the same chunk was sent (workers can finish out of order) or when the map was regenerated (`reset`).
- Gameplay never waits for meshes: it reads the density grid on the main thread, so determinism is untouched. The new crater appears one or two frames after the carve.

Measured on a desktop browser (Ricardo's PC, 4 workers), explosions of 2–8 chunks: main thread 0.3–1.6 ms (copy, post, upload), worker 2–5 ms, on screen after 2–7 ms. On the main thread the same explosions cost 2.5–11.7 ms. Initial mesh of the 18 chunks: ~15 ms until on screen. The stats line in the menu and the frame-time readout (fps · p95 · worst) show these numbers live, also on a phone.

On a Samsung Galaxy S23 Ultra (a high-end phone, 120 Hz screen; Chrome over `npm run dev:lan`): ~65 fps, p95 16.7 ms, worst frame usually ~17 ms with rare spikes up to ~58 ms (cause not found yet); a remesh costs the main thread 1.8 ms; generating the map 145–151 ms (main thread, once per match); initial mesh 36 ms warm (308 ms on the very first load, while the workers start).

## Performance path (in this order, always measuring)

1. **Web Worker for meshing.** Done (Phase 3): see "Meshing workers" above. Explosions cost the main thread ~1–2 ms instead of up to ~16 ms.
2. **WASM (Rust)** for the mesher/noise **only if** the benchmark shows JS is the limit after the Worker.
3. **Compute shaders (WebGPU)** only if CPU/WASM meshing is still the bottleneck; this needs a CPU copy of the grid for gameplay, and GPU→CPU readback has latency (tolerable in a turn-based game).
4. On the render side: per-chunk frustum culling (three.js already does it), LOD for distant chunks, and measuring on phones.

## Multiplayer (plan)

Turn-based and deterministic: client and server exchange **events** (map seed, shots with angle/power/weapon), and everyone simulates the same result. Hence the strict determinism rule. The server (technology to be decided) manages rooms and validates turn order.
